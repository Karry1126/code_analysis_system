### 人工指标怎么填


| 指标     | 选项                |
| ------ | ----------------- |
| 正确性    | `对` / `部分对` / `错` |
| 幻觉率    | `低` / `中` / `高`   |
| 工具调用质量 | `好` / `一般` / `差`  |
| 稳定性    | `稳定` / `不稳定`      |


- **正确性**：有没有答到点、改对了、漏没漏关键逻辑。
- **幻觉率**：有没有编造不存在的模块、文件、字段、结论。
- **工具调用质量**：路径对不对、有没有乱搜、该读的文件有没有读到。
- **稳定性**：有没有中途崩、死循环、被截断。

**本轮结论：**

- 表现好的题：
  - 告诉我 plt 有哪些模块内容
  - 告诉我生日礼包活动的生日命中逻辑

- 主要问题：
  - message合法性：会截断tool calling和tool result
  - message轮次维护：按轮次维护message有问题，会出现token爆的情况
  - `search_text` 太暴力了，未对检索数据进行加权，计算较久，且prompt数据量太多，会超上限
- 次要问题：
  - ai的兜底策略：会有多余的工具调用，属于**过度防御**
  - function call的决策会不稳定
  - token需要进统计系统，方便规划实际生产环境中的token消耗以及涉及token上限，以及超上限的异常处理
- 总结：对于企业级的业务内容，提出问题所需要引用的数据量级是一个关键指标，通过实践可以看出，如果引用的数据量小（目录级别或小型活动），则LLM可以正确回答，虽然中间的function call有时会不稳定，但不影响最终结果，如果引用的数据量大（跨模块咨询或中大型活动），则prompt会超1M的限制，这点可以考虑用RAG做优化；其次是对于Message，结构合法性的保护是必须的，对于message的维护应该使用token数量，而不是轮次，在生产环境中，需要对message使用的token数量做统计监控，及时调整策略以及agent的优化，若后续对长对话有需求，也可以引入Message的记忆功能。对于function call引用不稳定，有以下优化思路：prompt、工具描述、few-shot、路由策略
