你的痛点里，T01、T03、T04、T09、T10 本质都是同一个问题："plt 下有哪些 X" 这类集合查询，用 grep 是错的工具。grep 适合"定位一个已知符号"，不适合"枚举一个集合"。

## 真正的企业级代码问答系统（比如 Sourcegraph Cody、Cursor 的 codebase Q&A）都是这么组合的：
用户模糊提问
  ↓
[结构化层] 仓库地图 / 符号索引 / 依赖图  ← 你缺的就是这层
  ↓
[检索层] 结构化查询优先，向量检索兜底
  ↓
[验证层] 完整性检查（total vs returned）
  ↓
[LLM 层] 只在确定的信息上下结论

# deepseek 说
把"通用文件工具"升级成"三层检索系统"
第 0 层：仓库结构索引（离线构建，运行时只读）
  - 扫描 COMPANY_CODE_REPO_PATH，为每个模块目录生成一条 module card :卡片字段应该由“你想问什么问题”决定，而不是由“模块有什么共性”决定。
  - 生成一份 全局 include 倒排索引
  - 生成一份 模块名/别名倒排索引
第 1 层：模块内检索（现有 retrieve_code / search_text 收敛到模块粒度）
第 2 层：跨模块聚合（新增 aggregate_search 工具）
第 3 层：精读与验证（现有 read_text_file 保持，但加"读过的窗口"记账）

# 落地路线（分阶段，每阶段都独立可用）
```
阶段 0：离线索引管道

扫描仓库 → 识别模块 → 抽取符号/引用/include/配置键 → 写入索引。

增量更新：按文件 mtime 或 git diff 更新。

产物：符号倒排、include 图、模块元数据、配置键索引。

阶段 1：符号与引用工具

find_symbol_definition、find_symbol_references、query_include_graph。

结果按模块聚合，带覆盖度。

这一步做完，"任意组件使用方"这类问题就从"撞"变成"查"。

阶段 2：查询规划层

实体消歧规则（别名表 + 分词 + 领域词表）。

问题类型 → 算子组合的映射。

消歧失败显式报错 + 全文回退。

阶段 3：覆盖度与分页框架

所有工具统一返回 scanned / matched / unmatched / has_more / confidence。

Agent 的 runtime message 里显示"上一轮检索覆盖度"，让 LLM 自己判断要不要继续。

阶段 4：全文索引与语义层（可选）

接 Zoekt 或自建 trigram 索引，做低置信度回退。

向量检索放在最后，用于注释/文档/自然语言场景。

阶段 5：任务类型分流

在 runtime 层区分 enumerate / locate / trace / edit，分别给不同的算子偏好和循环预算。这一步是"用得好"，不是"能不能用"。
```
